# 建模引擎设计规范

> 本文档定义建模引擎的**通用思考规范**——跨领域的原则、阻断检查、依赖排序和完整性校验。
> 各工具的具体思考点和参数格式见 `references/modeling-sdk-reference.md`。

---

## 核心原则

**AI 负责思考，SDK 负责执行。** 调用 SDK 前必须完成所有业务分析，SDK 只管执行不做分析。

### 思考维度

- **业务视角**：业务需要啥，不是"技术上能做什么"
- **使用者视角**：一线操作员打开页面想先看到什么
- **数据流转**：哪些是源头、哪些是带出来的、哪些是算出来的
- **边界**：极端情况怎么处理
- **克制**：只思考必须的，别替用户决定不需要的

### 执行前阻断检查

> 调用 SDK 前必须通过，否则不得调用。禁止用"SDK 会自动处理"作为跳过分析的理由。

| 环节 | 必须输出的分析内容 | 禁止行为 |
|------|------------------|---------|
| **浏览框依赖** | 输出依赖分析图，标注哪些表单字段使用哪个浏览框（系统/自定义），环形依赖标注处理策略 | 不分析依赖顺序直接创建表单 |
| **布局分组** | 每组名称 + 包含字段列表 | 无分组方案直接调 SDK |
| **查询字段排序** | 显示顺序及理由 | 直接用表单默认顺序 |
| **快捷搜索** | 谁在查、怎么搜、选几个 | 不思考直接选前几个字段 |
| **浏览框字段** | 展示/链接/查询字段角色划分 | 直接用 SDK 默认的前 N 个字段 |

> 各思考点的具体内容见 `references/modeling-sdk-reference.md` 中对应工具的"思考点"章节。

### 各能力域强制规范

| 能力 | 强制要求 |
|------|---------|
| **应用** | 新功能模块必须新建应用，不允许复用已有应用；所有应用必须创建在「AI实践应用」下；**创建前必须先查询该应用的 ID，禁止硬编码** |
| **表单** | 必须提供完整数据模型（字段类型、长度、浏览框ID/选项等），禁止依赖 SDK 自动推断 |
| **模块** | ① 必须创建新建、编辑、查看三种布局 ② 必须设置权限 ③ 根据业务场景分析是否需要字段联动，不得跳过 |
| **查询列表** | ① 必须设置字段定义（显示列、顺序、查询条件） ② 必须设置 1~4 个快捷搜索条件 ③ 必须设置权限 |

## 1. 依赖排序

执行步骤必须有正确的依赖顺序。

**依赖判定规则：**

| 场景 | 依赖方向 |
|------|---------|
| 表单 A 字段使用浏览框 B | B 先于 A |
| 浏览框 B 引用表单 A | A 先于 B |
| 模块 M 引用表单 A | A 先于 M |
| 查询 Q 需要模块 M | M 先于 Q |
| 链式依赖 | A → B → C |

**环形依赖处理**（表单引用自身）：跳过该字段 → 创建浏览框 → `add_fields_to_form` 补加。两表单互引用：先各自跳过 → 创建两个浏览框 → 各自补加。

**自定义浏览框字段依赖处理**（表单字段引用尚未创建的自定义浏览框）：创建表单时跳过该字段 → 创建自定义浏览框 → `add_fields_to_form` 补加。

**输出要求：** 先输出依赖分析图，按依赖顺序排步骤。所有跳过的字段必须记录"跳过字段清单"：字段名、依赖的浏览框、补加时机。

> 详细推导规则见 `references/derivation-rules.md`

## 2. 建模要素完整性检查

**设计文档和开发设计阶段必须输出"建模要素对照表"，确保每个表单都有对应的模块和查询。**

各能力含义：菜单（入口）、应用（分组容器）、表单（骨架）、模块（卡片载体）、查询（列表页）、浏览框（选择器）。

**创建依赖链**：没有表单就没有模块，没有模块就没有查询，没有查询就没有菜单跳转目标。**默认每个表单都必须至少有一个模块和一个查询**（除非明确说"仅通过流程使用"）。

**强制输出：**
```
| 表单 | 模块 | 查询 | 浏览框 |
|------|------|------|--------|
| 表单A | 模块A | 查询A | 浏览框A |
```

**校验：** 表单、模块、查询列数量必须相等；任何一行中模块或查询为空必须说明原因。不确定时主动问用户"这个需要独立页面管理吗，还是通过流程/浏览框间接使用？"
