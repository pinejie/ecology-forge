# 执行 — 泛微二开

> 按开发设计文档逐一执行，一步一验证，做一步记一步。不跳步、不硬试、不闷头干到底、不反复卡确认。

---

## 核心原则

**严格按步骤顺序。** 开发设计里写了第 1 步到第 N 步，就按这个顺序来，不能跳、不能乱、不能自己发挥。有依赖关系的步骤必须等前置步骤完成才能开始。

**每步做完必验证。** 调了 SDK 不算完，要确认返回结果是成功的、数据是真的写进去了。比如 `create_form` 返回了 formid，再调 `get_form_detail` 查一遍确认。验证不过，后面别继续。

**出错了自己排。** 报错后先看错误信息，对照开发设计检查参数、顺序、环境，尝试修正后再执行。不要一出错就问用户"怎么办"。自己试了两次还不行，再把错误信息、做了什么尝试、怀疑什么原因，一起告诉用户。

**一路执行到底。** 中间有进度汇报，但不卡确认。全部完成后统一汇报结果。

**详细记录。** 调了哪个 tool、什么参数、返回什么、成功还是失败、花了多久，都记到 `{项目名}/04-执行记录.md` 里。不是写个"成功"就完了，以后出问题要能回溯。

**字段类型以开发设计文档为准。** 执行步骤中的 fields 参数必须携带完整字段类型定义（name、label、type、db_type/length/browser_id/options），按文档传入 SDK。禁止只看字段名就依赖 SDK 的 `_auto_detect_field_type` 自动推断——SDK 的兜底值（varchar 默认 100、float 默认 decimal(38,2)）会覆盖设计文档的精确值。如果开发设计文档中 fields 参数未携带类型，应先读取 `{项目名}/01-数据结构设计.md` 补齐后再执行。

**脏数据即时清理。** 测试调试产生的数据，用完就清。详细清理规则见 `references/dirty-data-cleanup.md`。

**建模缓存必须刷新。** SDK 通过 SQL 直连数据库创建模块/表单/查询/浏览框后，泛微的 `ModeComInfo`（模块→表单映射）和 `WorkflowBillComInfo`（表单→物理表映射）不会自动更新。不刷缓存的话，用户打开页面新增数据会失败（CubeDoSubmit 从缓存拿不到 formId/table）。所有步骤执行完毕后，必须调用 `modeCacheRefresh.jsp` 刷新建模引擎缓存。

**自动和手动衔接好。** SDK 能执行的部分直接干，手动部分给出清晰的步骤让用户照着做，确认用户做完了再继续后面的。不能把手动步骤糊弄过去。

**跳过字段必须补加。** 开发设计文档中标注"跳过"的字段（依赖自定义浏览框的字段），在浏览框创建完成后，必须用 `add_fields_to_form` 补加。跳过字段清单见 `{项目名}/01-数据结构设计.md`。补加前验证浏览框已存在，补加后验证字段类型正确（自定义浏览框 type=161，非系统浏览框 type=8）。

### 执行前思考验证点

> 以下参数在调用 SDK 前必须输出分析结果，否则不得调用。禁止用"SDK 会自动处理"作为跳过分析的理由。

| 涉及步骤 | 调用前必须输出 | 验证话术 |
|---------|--------------|---------|
| **布局配置** (`insert_layout`) | 分组方案：每组名称 + 包含字段列表 | "布局分组方案：{分组1名}: {字段列表} → {分组N名}: {字段列表}" |
| **查询字段** (`save_formfields`) | 字段显示顺序及理由 | "查询字段排序：{字段1}排第1因为... → {字段N}" |
| **快捷搜索** (`add_quicksearch_condition`) | 谁在查、怎么搜、选几个 | "快捷搜索：操作员查 → 用名称/编号搜 → 选X个字段" |
| **浏览框** (`create_browser`) | 展示字段、链接字段、查询字段划分 | "浏览框配置：istitle={X}, 展示={A,B,C}, 查询={D}" |

**反面示例：**
```
❌ "现在做布局配置，调用 insert_layout auto_group=True"
   → 未输出分组方案，SDK 自动分组不符合业务场景，跳过

✅ "现在做布局配置。项目申报分组方案：
    基本信息：项目名称、项目类型、项目负责人、所属部门
    时间信息：开始日期、结束日期
    经费信息：总预算、经费预算明细
    详情信息：项目摘要、申报附件
   → 调用 insert_layout 传入上述 config"
```

## 何时激活

**一定要用：**
- 开发设计文档已确认，用户说"开始执行"、"按方案干"、"第三步"、"照着做"
- 用户说"开干"、"开始干"、"动手"、"按这个来"
- 用户拿着 `02-开发设计.md` 说"照这个来"

**可以跳过：**
- 开发设计还没确认（回去走第二步）
- 就单独调一个接口、跑一条 SQL（不需要走完整执行流程）

## 执行流程

### 前置检查

开始前确认：
- [ ] `{项目名}/02-开发设计.md` 存在
- [ ] `{项目名}/03-测试文档.md` 存在
- [ ] MCP Server 可用，SDK 工具列表已确认
- [ ] 数据库连接正常

全部确认后直接开始，不需要等用户说"开始"。

### 创建执行记录

在 `{项目名}/` 下创建 `04-执行记录.md`。格式见 `template-execution-record.md`。

### 逐步骤执行

按开发设计的步骤序号，逐一执行。

**执行前：** 在对话中说清楚"现在做第 N 步 — {步骤名称}，会调用 XX 工具 / 执行 XX SQL"

**执行中：** 调用对应的 SDK tool / MCP tool / SQL

**执行后：**
1. 验证结果：调验证接口或查数据确认
2. 记录结果：写入 `04-执行记录.md`
3. 告知用户："第 N 步完成 — 已调用 XX，返回 XX / 查到 X 条数据。下一步做 YY。"

### 失败处理

某步执行失败时：

1. **看错误信息** — 分析完整响应体，找出具体报错原因
2. **对照开发设计** — 检查参数是否正确、步骤顺序是否正确、前置条件是否满足
3. **尝试修正** — 修正后重试 1 次
4. **记录失败** — 在 `04-执行记录.md` 中记录：错误信息、做了什么尝试、怀疑原因
5. **重试仍失败** — 停止执行，把排错过程和失败详情告诉用户，**不要反复重试同一请求**
6. **需要回退时** — 如果失败导致数据不完整，先清理这步产生的脏数据，再等用户指示

**排错参考：** 如果怀疑是 API 参数问题，对照 `~/.claude/rules/_global/api_call_debugging.md` 的规则排查。

### 手动步骤处理

遇到标注"手动"的步骤：

1. 把操作步骤完整展示给用户，说清楚要做什么
2. 用户做完后确认"做完了"
3. 用 SDK 或 SQL 验证用户操作结果
4. 验证通过才继续下一步

### 全部完成

所有步骤执行完成后：
1. **刷新建模缓存** — HTTP GET `{OA_HOST}/modeCacheRefresh.jsp`，确认返回 `{"status":"1",...}`。失败则重试 1 次，仍失败则在执行记录中注明并告知用户手动重启服务。
2. 在 `04-执行记录.md` 末尾写"全部步骤执行完毕"+ 缓存刷新结果
3. 统计：成功 X 步、失败 Y 步、手动 Z 步
4. 告诉用户："执行完成，{统计}。缓存已刷新。下一步对照测试文档做整体验收。"

## 反面模式

| 反面模式 | 为什么不对 | 正确做法 |
|---------|-----------|---------|
| 跳着执行，先做简单的 | 依赖关系乱了，后面跑不通 | 严格按步骤序号来 |
| 调了 SDK 就算完 | 可能返回了失败但没发现 | 调完必验证 |
| 一报错就问用户 | 用户不想当排障工具人 | 先看错误、再修正、再重试 |
| 反复重试同一请求 | 浪费 token 还掩盖问题 | 试两次不行就停，说清楚 |
| 执行中途卡确认 | 开发设计已确认，反复停下来纯属拖节奏 | 一路执行到底，完成统一汇报 |
| 执行记录只写"成功" | 出问题没法回溯 | 参数、返回、时间都记 |
| 只看字段名不传类型就调 SDK | SDK 自动推断的兜底值会覆盖设计文档的精确类型 | 按开发设计文档的 fields 参数完整传入，含 type、db_type/length/browser_id/options |
| 手动步骤糊弄过去 | 用户不知道要做什么 | 给清楚步骤，确认做完了 |
| 测试数据留着不清 | 正式执行时冲突 | 用完就清，见脏数据清理规则 |
| 布局/查询/搜索不分析直接调 SDK | SDK 自动处理不符合业务场景 | 调 SDK 前先输出分组方案、排序逻辑、搜索字段及理由 |
| 跳过字段忘了补加 | 表单缺失关键字段 | 按数据结构设计文档的"跳过字段清单"逐一补加，补完核对数量 |

## 正面模式

- 严格按步骤顺序，一步一验证
- 出错了先自己排，修好了再继续
- 一路执行到底，不反复卡确认
- 执行记录详细到能回溯
- 脏数据即时清理，不留尾巴
- 手动步骤给清楚，确认完了再往下
- **调 SDK 前先思考**：布局分组、查询排序、快捷搜索等需要业务判断的参数，先输出分析再调用
- **创建表单时跳过依赖自定义浏览框的字段**，等浏览框创建后统一用 `add_fields_to_form` 补加。补加后验证字段类型（type=161 而非 type=8）
