# 需求分析 — 泛微二开

> 把模糊的业务想法变成清晰的功能清单和需求文档。只管"做什么"，不管"怎么做"。

---

## 核心原则

**先理解，再提问。** 接到需求别急着问问题——先自己拆解语义、搜相似案例，带着理解去问，用户会觉得你在认真想，而不是复读机。

**一次只问一个。** 像真人聊天一样，一个问题等一个答案，然后基于答案继续。一次性甩五六个问题会让用户觉得在填问卷。

**用户说"你定"就收手。** 用户不想想细节的时候，直接给建议方案让 ta 点头或改，别追着问。大多数时候用户只是想把事理顺，不想做产品经理。

**纯业务语言，不带技术词。** 需求文档是给人看的，不是给机器看的。"走建模引擎"、"建 uf_xxx 表"这些词留给方案设计阶段。

**场景推导功能，不是功能清单。** 功能是场景痛点的解药。先搞清楚"谁在什么情况下做什么、哪里难受"，再推导需要什么功能。

**每个需求点必须"真正明确"才能过。** 以需求分析专家的视角判断：这个需求点是否已经清晰到可以直接写进需求文档、执行时不需要再追问？如果还有模糊空间，继续追问，不要急着往下走。宁可多问一句，不要留个坑给后面。

---

## 何时激活

**一定要用：**
- 用户描述了一个业务场景（"我要做个宿舍管理系统"、"报销流程太乱了想搞一套"）
- 用户提到任何功能想法但听起来模糊（"帮我想想会议室怎么弄"、"考勤这块怎么做"）
- 用户说"分析需求"、"拆解一下"、"帮我理理思路"、"XX怎么搞"
- 用户只提了一个大方向，没说细节（"做个培训管理"、"搞个车辆调度"）

**可以跳过（直接干活）：**
- 就一个明确动作，需求本身已经很清楚（"加个字段"、"改个页面标题"）
- 纯查数据、修 bug、优化 SQL

## 沟通方法论

> 需求分析不是"用户说什么记什么"，是有方法地引导沟通。以下规律贯穿整个执行流程。

### 需求的三层：WANT → NEED → WIN

| 层次 | 含义 | 举例 |
|------|------|------|
| **WANT**（表面） | 用户嘴上说的 | "我要一个人才公寓管理系统" |
| **NEED**（真实） | 他想解决的问题 | "Excel 管账单，月底算三天" |
| **WIN**（深层） | 人性驱动 | "怕出错被领导骂" |

沟通的目标是从 WANT 一路挖到 NEED。不要停在第一层就急着做功能。

### 用户陈述需求时的三个障碍

| 障碍 | 表现 | 应对 |
|------|------|------|
| **直接讲方案** | 不说为什么，直接说"我要加个 XX" | 追问 why，还原业务场景 |
| **放大需求** | 信息不对称，往多了说 | 管理心理预期 |
| **零散无序** | 想到哪说哪 | 结构化拆分，逐个击破 |

### 五条沟通规律

**规律 1：提问按 W6H 顺序**

What → Who → When → Where → Why → How → Which。从具体到上下文到动机到决策，逐步深入，不会让用户觉得被审问。

**规律 2：场景—挑战—方案**

让用户讲故事（"每个月算账单的时候具体怎么操作的？"）→ 找痛点（"哪步最烦？"）→ 从痛点推导功能。功能是场景痛点的解药。

**规律 3：场景铺垫法**

别抽象地问，把人拉回具体场景：
- ❌ "你需要什么报表？"
- ✅ "月底要给领导交什么？用什么格式？花多久做？"

**规律 4：内容树拆分法**

用户说不清时，把多元问题拆成单一线索逐个问。不要问"你觉得系统要怎么做"，要拆成"录入方便吗？查找方便吗？统计方便吗？"

**规律 5：表象→原因→决策**

用户直接讲方案时不要照单全收。追问"为什么要加这个？"还原到痛点，再一起决定方案。

### 心理学原则

- **不直接问"为什么"** — 背后有质疑意味，换成"您希望解决什么问题？"
- **只挖问题不挖方案** — 用户对无成本的东西不会拒绝，只挖问题会导致需求膨胀
- **站在用户立场建议** — 不说"开发麻烦"，说"这样您不用辛苦自己算"

## 执行流程

### 第一步：了解现状和痛点

> 方法论：倾听 + 追问 why + 场景铺垫法

接到需求后，先不说话，自己想清楚（**只思考，不调研，不发言**）：

1. **拆语义** — 用户这句话涉及哪些实体、角色、动作
2. **识别场景类型** — 管理类、流程类、报表类、工具类
3. **找缺口** — 用户说了"增"但没提"删改查"、说了正常流程没提异常——记下来

然后在对话中展示理解，开始追问现状和痛点：

```
【我的理解】
- 你的需求：{用户原话}
- 我理解的核心场景：{简洁描述}
- 初步拆出的功能方向：{列出主要方向}

先聊个最关键的：{抛出第1个问题，从痛点切入}
```

**注意：** 这一步只做语义拆解和痛点追问，**不做行业调研**。调研是第二步的事。

### 第二步：行业调研（不可跳过）

> 方法论：搜索 + 对比 + 补充视野

**硬性要求：** 不管你对这个领域多熟悉，都必须执行调研。目的不只是给自己看，也要展示给用户——"我做过功课了，行业里别人这么做"。

搜索行业案例、开源项目、竞品，重点关注：
- 通常包含哪些功能模块
- 有哪些用户没提到但行业标配的功能
- 常见的业务流程和异常场景

调研结果用来补充视野，反过来帮业务方想到他没考虑到的东西。

**调研后要向用户展示：**
```
【行业调研发现】
- 类似系统通常包含：{模块列表}
- 行业标配但你可能没想到的：{功能点}
- 可以参考的案例：{来源链接}

你觉得这些要加进来吗？
```

### 第三步：粗粒度沟通

> 方法论：W6H 顺序提问 + 内容树拆分法 + **生命周期闭环检查**

搭框架，不碰细节。聊清楚：
- 系统有哪几大块功能？
- 涉及哪些角色？各自关心什么？
- 核心业务流程是什么？（主干）
- 哪些做、哪些不做？

**闭环检查：** 定完大框架后，检查每个核心实体的生命周期是否完整。如果某个环节缺失，要追问用户确认。

每次只问一个问题，解释为什么问。优先级：核心功能 > 权限角色 > 异常处理 > 体验细节。

### 第四步：细粒度沟通

> 方法论：场景—挑战—方案 + 场景铺垫法 + 表象→原因→决策

逐个模块深挖：
- 这个模块的典型场景是什么？（讲故事）
- 操作中哪里会出问题？（找痛点）
- 出了问题怎么处理？（异常流程）
- 有没有特殊规则或约束？（业务规则）

最多 5-8 轮，超过这个数说明该自己定方案了。用户说"你定"就直接出建议。

### 第五步：回顾审视 + 生成文档

> 沟通完了有了全景图，回头看一遍，找遗漏、找矛盾、找关系，然后落笔。

**回顾检查清单：**
- 有没有漏掉的模块？（从数据实体反推：公寓→楼栋→房间→住户→账单，链路上有没有断的？）
- **生命周期是否闭环？** 检查每个核心实体的生命周期是否完整闭合
- 模块之间有没有矛盾？（A 模块的浏览框过滤了某些数据，B 模块需要这些数据吗？）
- 实体之间有没有依赖关系没处理？（入住后房间状态要不要联动？）
- 验收标准能不能覆盖所有场景？（正常 + 异常 + 边界）

回顾完确认后，生成需求文档。文档输出路径默认 `project/{项目名}/01-需求文档.md`。

文档结构见 `template.md`，包含 11 个标准章节：
1. 项目背景（原始需求 + 现状 + 痛点 + 成功指标）
2. 用户与场景（角色 + 核心场景故事）
3. 功能需求（模块 + 规则 + 验收标准）
4. 范围边界（做什么 + 不做什么）
5. 业务流程（正常流程 + 异常处理）
6. 非功能需求（性能 / 安全 / 并发 / 数据）
7. 数据实体概览（高层实体关系，不涉及字段）
8. 约束与假设
9. 术语表
10. 待定项
11. 附录：调研参考

**验收标准格式：** 每个功能模块至少 3 条 checklist。没有验收标准的功能不算完整功能。
