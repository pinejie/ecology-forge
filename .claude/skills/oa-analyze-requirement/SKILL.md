# 需求分析 — 泛微二开

> 把模糊的业务想法变成清晰的功能清单和需求文档。只管"做什么"，不管"怎么做"。

---

## 核心原则

**先理解，再提问，一次只问一个。** 接到需求先自己拆解语义、带着理解去问。一个问题等一个答案，然后基于答案继续，别一次甩五六个问题让用户觉得在填问卷。

**能追就追到位，追不动就自己拍板。** 用户愿意聊时，每个点追问到能直接写进需求文档。用户流露出倦意就收——先判断是一个点不想展开，还是整体都不想聊了。不想聊的部分，AI 自己拍板出方案，标清楚"这块我替你做主了"，让用户扫一眼就行。

**纯业务语言，不带技术词。** 需求文档是给人看的，不是给机器看的。"走建模引擎"、"建 uf_xxx 表"这些词留给方案设计阶段。

**场景推导功能，不是功能清单。** 功能是场景痛点的解药。先搞清楚"谁在什么情况下做什么、哪里难受"，再推导需要什么功能。

---

## 何时激活

**一定要用：**
- 用户描述了一个业务场景（"我要做个宿舍管理系统"、"报销流程太乱了想搞一套"）
- 用户提到任何功能想法但听起来模糊（"帮我想想会议室怎么弄"、"考勤这块怎么做"）
- 用户说"分析需求"、"拆解一下"、"帮我理理思路"、"XX怎么搞"
- 用户只提了一个大方向，没说细节（"做个培训管理"、"搞个车辆调度"）

**可以跳过（直接干活）：**
- 就一个明确动作，需求本身已经很清楚（"加个字段"、"改个页面标题"）
- 纯查数据、修 bug、优化 SQL

---

## 沟通方法论

> 需求分析不是"用户说什么记什么"，是有方法地引导沟通。

**表层需求背后挖真实痛点。** 用户说"我要一个 XX 系统"，背后通常是"现在用 Excel 算，太慢了"。别停在第一层就急着做功能。

**提问从具体到抽象，逐步深入。** What → Who → When → Where → Why → How → Which。让用户讲实际场景（"月底怎么操作的？"），从痛点推导功能，别问抽象问题（"你需要什么报表？"）。

**用户说不清时，拆成单一线索逐个问。** 不要问"系统要怎么做"，要拆成"录入方便吗？查找方便吗？统计方便吗？"

**用户直接讲方案时，先追问背后的痛点再决定。** 不照单全收，也不直接否定。换个问法：不说"为什么"，说"您希望解决什么问题？"

---

## 执行流程

### 第一步：了解现状和痛点

1. **拆语义** — 用户这句话涉及哪些实体、角色、动作
2. **识别场景类型** — 管理类、流程类、报表类、工具类
3. **找缺口** — 用户说了"增"但没提"删改查"、说了正常流程没提异常——记下来

想清楚后，在对话中展示理解，开始追问现状和痛点：

```
【我的理解】
- 你的需求：{用户原话}
- 我理解的核心场景：{简洁描述}
- 初步拆出的功能方向：{列出主要方向}

先聊个最关键的：{抛出第1个问题，从痛点切入}
```

**注意：** 这一步只做语义拆解和痛点追问，**不做行业调研**。调研是第二步的事。

### 第二步：行业调研

> 方法论：搜索 + 对比 + 补充视野

需求复杂度决定调研深度。简单的改动（加字段、改标题）可以跳过调研；涉及新功能模块或业务流程的，必须搜索行业案例。目的不只是给自己看，也要展示给用户——"我做过功课了，行业里别人这么做"。

搜索行业案例、开源项目、竞品，重点关注：
- 通常包含哪些功能模块
- 有哪些用户没提到但行业标配的功能
- 常见的业务流程和异常场景

调研结果用来补充视野，反过来帮业务方想到他没考虑到的东西。

**调研后要向用户展示：**
```
【行业调研发现】
- 类似系统通常包含：{模块列表}
- 行业标配但你可能没想到的：{功能点}
- 可以参考的案例：{来源链接}

你觉得这些要加进来吗？
```

### 第三步：逐层深入沟通

先搭框架（哪些功能模块、哪些角色、主干流程、做不做），再逐模块深挖（典型场景、痛点、异常流程、业务规则）。每次只问一个问题，优先级从核心功能到体验细节逐步递进。

**闭环检查：** 每个核心实体的生命周期是否完整，缺失环节要追问确认。

沟通中用户不想继续某个点时，按核心原则"能追就追到位，追不动就自己拍板"处理。

### 第四步：回顾审视 + 生成文档

> 沟通完了有了全景图，回头看一遍，找遗漏、找矛盾、找关系，然后落笔。

**回顾检查清单：**
- 有没有漏掉的模块？（从核心实体反推完整链路，链路上有没有断的？）
- **生命周期是否闭环？** 检查每个核心实体的生命周期是否完整闭合
- 模块之间有没有矛盾？（A 模块的浏览框过滤了某些数据，B 模块需要这些数据吗？）
- 实体之间有没有依赖关系没处理？（入住后房间状态要不要联动？）
- 验收标准能不能覆盖所有场景？（正常 + 异常 + 边界）

回顾完确认后，生成需求文档。文档输出路径默认 `project/{项目名}/01-需求文档.md`。

文档结构见 `template.md`，包含 11 个标准章节：
1. 项目背景（原始需求 + 现状 + 痛点 + 成功指标）
2. 用户与场景（角色 + 核心场景故事）
3. 功能需求（模块 + 规则 + 验收标准）
4. 范围边界（做什么 + 不做什么）
5. 业务流程（正常流程 + 异常处理）
6. 非功能需求（性能 / 安全 / 并发 / 数据）
7. 数据实体概览（高层实体关系，不涉及字段）
8. 约束与假设
9. 术语表
10. 待定项
11. 附录：调研参考

**验收标准格式：** 每个功能模块至少 3 条 checklist。没有验收标准的功能不算完整功能。
