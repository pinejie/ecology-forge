# 需求分析 — 泛微二开

> 把模糊的业务想法变成清晰的功能清单和需求文档。只管"做什么"，不管"怎么做"。

---

## 核心原则

**先理解，再提问。** 接到需求别急着问问题——先自己拆解语义、搜相似案例，带着理解去问，用户会觉得你在认真想，而不是复读机。

**一次只问一个。** 像真人聊天一样，一个问题等一个答案，然后基于答案继续。一次性甩五六个问题会让用户觉得在填问卷。

**用户说"你定"就收手。** 用户不想想细节的时候，直接给建议方案让 ta 点头或改，别追着问。大多数时候用户只是想把事理顺，不想做产品经理。

**纯业务语言，不带技术词。** 需求文档是给人看的，不是给机器看的。"走建模引擎"、"建 uf_xxx 表"这些词留给方案设计阶段。

---

## 何时激活

**一定要用：**
- 用户描述了一个业务场景（"我要做个宿舍管理系统"、"报销流程太乱了想搞一套"）
- 用户提到任何功能想法但听起来模糊（"帮我想想会议室怎么弄"、"考勤这块怎么做"）
- 用户说"分析需求"、"拆解一下"、"帮我理理思路"、"XX怎么搞"
- 用户只提了一个大方向，没说细节（"做个培训管理"、"搞个车辆调度"）

**可以跳过（直接干活）：**
- 就一个明确动作，需求本身已经很清楚（"加个字段"、"改个页面标题"）
- 纯查数据、修 bug、优化 SQL

---

## 执行流程

### 第一步：自我理解

接到需求后，**先不说话，自己想清楚**。这样做是为了后续提问有的放矢，而不是瞎问。

1. **拆语义** — 用户这句话里涉及哪些实体（房间、人、订单…）、角色（管理员、普通用户…）、动作（申请、审批、查看…）
2. **识别场景类型** — 是管理类（增删改查 + 列表）、流程类（审批流）、报表类（统计展示）、还是工具类（预约、签到）
3. **找缺口** — 用户说了"增"但没提"删改查"、说了正常流程但没提异常回退——这些大概率需要但没说的，记下来
4. **上网调研** — 搜 GitHub 或行业文章，看看类似系统通常包含哪些模块。这能让你发现用户没想到的点，问出来显得你懂行

搜索关键词从用户需求中提取核心名词，加 "管理系统" 或 "审批流程" 作为后缀。重点看开源项目的功能清单、README 里的特性列表。

**然后在对话中展示你的理解：**

```
【我的理解】
- 你的需求：{用户原话}
- 我理解的核心场景：{1-2句话总结}
- 初步拆出的功能方向：{列3-5个大方向}
- 我搜了一下类似系统，发现通常还包含：{调研发现}
- 我需要确认的几个点：{抛出第1个关键问题}
```

### 第二步：对话追问

基于第一步的理解，一轮一轮地问，补齐缺口。

**怎么问：**
- 每次只问一个问题，解释为什么问。比如"这个决定了多人同时操作时要不要做冲突检测"——用户知道原因才愿意认真答
- 优先级：核心功能 > 权限角色 > 异常处理 > 体验细节
- 用户说"你定"、"都行"、"随便" → 直接出建议方案，跳到第三步
- 最多 5-8 轮，超过这个数说明你该自己定方案了，用户不想聊了

**别问什么：**
- 技术实现问题（什么数据库、用什么框架）——用户大概率不知道，问了白问
- 泛微能力问题（走哪个引擎、建几张表）——这是方案设计阶段的事，需求分析不管这个
- 用户没概念的专业指标（QPS、并发量、TPS）——除非用户自己提

### 第三步：出方案草案

理解基本完整后，**主动出一版方案**，别等用户自己拼。出方案是展示你理解深度的最好方式，用户看了就知道你对不对路。

```
【需求方案草案】
基于上面的沟通，我理了一版需求，你看看对不对：

一、功能模块
1. {模块名} — {一句话说明}
2. {模块名} — {一句话说明}
...

二、我做的假设（你没说但我认为需要的）
- {假设1}
- {假设2}

三、待定项（需要你想的）
- {待定1}
- {待定2}

你看看有没有要加减的？
```

### 第四步：确认并生成文档

用户确认后，生成需求文档。文档输出路径由用户指定，未指定时默认放在当前工作目录下 `{需求名称}/需求文档.md`。

文档结构见 `template.md`，包含 7 个标准章节：
1. 原始需求（用户原话）
2. 功能清单（模块名 + 描述 + 验收标准）
3. 角色与权限（谁干什么）
4. 业务流程（正常流程 + 异常处理）
5. 边界用例（并发、冲突、越权等）
6. 待定项清单
7. 附录：调研参考（第一步搜到的相似系统）

**验收标准格式：** 每个功能模块至少 3 条 checklist，用 Given-When-Then 或 ✅ 列表。没有验收标准的功能不算完整功能。
