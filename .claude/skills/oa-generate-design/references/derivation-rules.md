# 建模引擎逆向推导规则

> 接到需求后，从终点能力倒推出完整开发链。倒推结果反过来就是正向执行顺序。

---

## 一、场景识别

先看需求描述，判断属于哪个能力域：

| 关键词/描述 | 能力域 |
|------------|--------|
| "表单"、"字段"、"增删改查"、"查询列表"、"浏览框"、"菜单" | 建模引擎 |
| "审批"、"流程"、"节点"、"流转"、"会签"、"转交" | 流程引擎 |
| "移动端"、"H5"、"小程序"、"企微" | 移动建模 |
| "定时"、"轮询"、"自动执行"、"计划任务" | 定时任务 |
| 多个混合 | 多域混合，按域拆分 |

识别后，到对应能力域继续推导。本文档只覆盖**建模引擎**的推导规则。

---

## 二、逆向推导思维

建模引擎的每个能力都不是孤立的。做一个能力之前，先问自己三个问题：

1. **这个能力挂在谁下面？** —— 找父能力，它需要谁的 ID 或容器
2. **这个能力依赖谁？** —— 找前置条件，没有谁它就不存在
3. **谁依赖它？** —— 找下游，做完了谁能用

从你最终要做的那个能力出发，一层层往外剥，剥到最上游（应用、表单）为止。

**核心认知**：后面的能力需要前面能力产出的 ID。没有 ID，后面的一切都干不了。

能力之间的依赖关系见 `references/capability-map.md` 的能力层级关系图。

## 三、倒推模板

### 通用公式

```
我要做 X
  → X 需要 Y 的 ID（或 Y 先存在）
  → Y 需要 Z 的 ID（或 Z 先存在）
  → ...
  → 剥到不能再剥为止

倒推完反过来，就是执行顺序：起点 → ... → Z → Y → X
```

### 常见倒推链

**我要做个查询列表**
```
查询 → 需要模块 ID → 模块需要表单 ID + 应用 ID → 表单需要字段
倒推：应用 → 表单+字段 → 模块 → 查询
```

**我要加个浏览框**
```
浏览框 → 需要表单字段来构建字段配置 → 表单需要已存在
倒推：表单 → 浏览框
```

**我要做个字段联动**
```
字段联动 → 挂在模块下 → 模块需要表单 → 表单需要字段
倒推：表单+字段 → 模块 → 字段联动
```

**我要挂在左侧菜单上**
```
菜单 → 需要查询 ID 拼接链接 → 查询需要模块 ID → 模块需要表单 + 应用
倒推：表单 → 模块 → 查询 → 菜单
```

**我要做一套完整功能**
```
完整功能 → 菜单需要查询 → 查询需要模块+字段 → 模块需要表单+应用
倒推：应用 → 表单+字段 → 模块 → 查询 → 菜单
```

## 四、正向执行顺序

倒推结果反过来，就是正向执行顺序：

| 步骤 | 动作 | 产出 | 下游谁需要 |
|------|------|------|-----------|
| 1 | 确认/创建应用 | 应用 ID | 模块 |
| 2 | 创建表单 + 字段 | 表单 ID + 字段列表 | 模块、查询、浏览框、布局、联动 |
| 3 | 刷新缓存 | — | 让 label 生效 |
| 4 | 创建模块 | 模块 ID | 查询、布局、联动 |
| 5 | 创建查询列表 | 查询配置 | 菜单、快捷搜索 |
| 6 | 配置布局/联动 | 布局 JSON + 联动规则 | 无下游 |
| 7 | 配置快捷搜索 | 快捷搜索条件 | 无下游 |
| 8 | 创建菜单 | 菜单项 | 无下游 |

**按需裁剪**：不是每一步都要做，根据需求提取对应的步骤子集。比如只需要查询页面就做 1→2→4→5→8，不需要 6 和 7。

---

## 五、注意事项

- **菜单是独立的**——不属于任何能力树节点，只是把模块/查询"暴露"到导航上
- **浏览框是独立的**——跨模块复用，但字段配置依赖表单
- **一个模块可以有多个查询列表**——开发设计时通常先做主查询
- **模块创建时会自动查找同名已有模块**——可能复用现有表单和应用信息，不一定从零开始

## 六、自定义浏览框字段依赖处理

表单字段引用自定义浏览框时，存在"先有鸡还是先有蛋"的问题：浏览框需要表单先存在（数据源），但表单字段又需要浏览框先存在（类型正确）。

### 识别规则

创建表单前，逐个分析浏览框字段：

| 判断条件 | 浏览框类型 | 处理方式 |
|---------|-----------|---------|
| 字段指定的 browser_name 在 mode_custombrowser 中已存在 | 自定义浏览框 | 直接创建字段 |
| 字段指定的 browser_name 在 mode_custombrowser 中不存在 | 自定义浏览框（待创建） | 跳过该字段，等浏览框创建后补加 |
| 字段指定 browser_id（系统浏览框 ID） | 系统浏览框 | 直接创建字段 |

### 处理策略

**两步走：跳过 → 补加**

1. **创建表单时**：跳过所有依赖"尚未创建的自定义浏览框"的字段
2. **创建自定义浏览框后**：用 `add_fields_to_form` 补加跳过的字段

### 输出要求

数据结构设计文档中必须输出"跳过字段清单"：

```
| 表单 | 跳过字段 | 依赖的浏览框 | 补加时机 |
|------|---------|------------|---------|
| 初审审核 | project_ref | 项目浏览框 | Phase 3（浏览框创建后） |
| 专家评审 | project_ref | 项目浏览框 | Phase 3 |
```

### 反面案例

```
❌ 创建表单时直接传入自定义浏览框字段 → SDK auto-detect 匹配到系统浏览框，字段类型错误
❌ 用系统浏览框占位 → 后续替换浏览框时可能引发字段元数据不一致
✅ 创建表单时跳过 → 浏览框创建后补加 → 字段类型正确
```
