# 方案设计 — 泛微二开

> 拿着需求文档，逐条功能清单分析，对照泛微能力，一次性出齐三份文档（数据结构+开发设计+测试）。不卡确认、不凑字数、不做空中楼阁。

---

## 核心原则

**有依据才设计。** 每个设计项都对应需求文档编号，不自编需求。没找到 `01-需求文档.md` 就告诉用户先完成需求分析。

**能力文档是边界。** 以 `references/capability-map.md`（能做什么）和 `references/modeling-sdk-reference.md`（怎么调用）为准。做不了直说，别糊弄。

**先了解平台再设计。** 设计任何组件之前，必须先读 `references/modeling-sdk-reference.md` 中**对应章节**的思考点（按需读取，不用全读），了解平台对这类组件提供了什么能力和约束，再结合需求做设计。禁止不看平台能力就凭直觉设计方案。

**一次出齐，不卡确认。** 需求文档已确认的前提下，三份文档一次性生成，不等用户确认中间产物。

**字段类型必须传递。** 开发设计文档执行步骤中的 fields 参数必须携带完整字段类型定义（name、label、type、db_type/length/browser_id/options），与数据结构设计文档逐字一致。

**步骤必须写到可执行粒度。** 开发设计文档的每个执行步骤，必须细到换一个 AI 来执行时不需要再思考、再猜测，照着做就行。禁止出现"各查询的快捷搜索条件"、"详见各模块的查询设计"这类模糊描述。每个查询配哪些字段、哪些做快捷搜索，必须逐一列明。

**设计完成后必须自检。** 三份文档生成后，逐一检查每个执行步骤：参数是否明确？是否能直接执行？如果遇到"不知道配什么"的步骤，说明设计阶段没想清楚，必须补齐再交付，不能留给执行阶段临场发挥。

**步骤数量必须对账。** 开发设计文档的步骤数 = 需求功能清单推导出的操作数。设计完成后数一遍：功能清单有 N 个操作，文档里是不是有 N 个步骤？少了就是漏设计，必须补上。


### 字段类型规则

> 设计阶段和执行阶段必须使用同一种语言——SDK 逻辑类型。物理类型由 SDK 自动转换，设计师不需要关心。

1. **设计文档的"字段类型"必须使用泛微逻辑类型**，禁止写物理类型（varchar/int/text 等数据库类型）。逻辑类型参考 `references/field-type-reference.md`。

2. **逻辑类型必须来自 SDK 合法清单**（18 种）：
   text、integer、float、amount、amount-format、textarea、browser、checkbox、dropdown、radio、multiselect、file、special、pubchoice、date、datetime、time、year

3. **每个字段必须写齐类型相关参数：**
   - text → length（默认 100，按实际需要标注）
   - dropdown/radio/multiselect → options（必传）
   - browser → browser_id（系统浏览框）或 browser_name（自定义浏览框），必传
   - float → db_type（如需覆盖默认 decimal(38,2)）
   - date/datetime/time/year → 无需额外参数，SDK 自动处理

4. **日期/时间字段必须用 date/datetime/time/year**，禁止用 text 模拟。用 text 创建出来的是文本输入框，不是日期选择器。

5. **业务→逻辑类型映射**参考 `references/field-type-reference.md` 的"业务场景 → 逻辑类型速查"章节，以及 `references/modeling-sdk-reference.md` 的"字段分析"部分。

方案设计依赖三类文档：

| 类别 | 文档 | 作用 |
|------|------|------|
| **需求文档** | `project/{项目名}/01-需求文档.md` | 功能清单、角色权限、业务流程、验收标准 |

## 何时激活

**一定要用：**
- 需求文档存在，用户说"出方案"、"写开发设计"、"做技术方案"、"第二步"、"怎么落地"
- 用户拿着需求文档问实现方案

**可以跳过：**
- 需求还没理清（回去走第一步）
- 就调一个已知接口、改一个已知字段

## 执行流程

### 第一步：场景定位

> 依据：`references/scenario-classification.md`

读取需求文档，逐条功能清单扫描关键词，判断属于哪个能力域。

**输入**：需求文档功能清单
**输出**：每条功能的能力域判定

```
【场景定位】
- F1 通知公告：命中"发布/编辑/停用/查看" → 建模引擎
- F2 项目审批：命中"审批/节点/流转" → 流程引擎
- F3 每日统计：命中"每日/自动执行" → 定时任务
```

多域混合时，按域拆分为独立子需求，分别走后续流程。

---

### 第一步半：提取验收标准（阻断检查）

> 设计前必须完成，禁止跳过。

读取需求文档，提取每个功能模块的**验收标准**，逐条标注关键词，明确实现方式。

**输出格式**（必须输出，禁止跳过）：

```
【验收标准提取】
F1 房源管理：
  - "可以创建公寓、楼栋、房间三级结构" → 3张表单 + 层级浏览框
  - "可以实时查看每个房间的状态" → 查询列表显示 room_status
  - "每个房间可以设置独立的月租价格" → 字段 monthly_rent
  - "每个房间可以录入配置的家具清单" → 主从表单（房间+家具明细）
  - "可以按状态筛选房间" → 快捷搜索 room_status

F2 入住管理：
  - "可以录入住户基本信息" → 字段：姓名、工号、子公司、联系方式
  - "可以为住户分配房间（只能选空置房）" → 关键词"只能"，需要创建"空置房间浏览框"，default_filter: room_status=0
  - "入住后房间状态自动变为'已入住'" → 关键词"自动"，需要联动或说明手动操作
  - "可以记录入住时的家具交接清单" → 明细表
```

**关键词处理规则**：

| 关键词 | 含义 | 设计要点 |
|--------|------|---------|
| "只能"、"必须"、"不允许" | 业务约束 | 浏览框过滤、字段校验、状态检查 |
| "自动" | 自动化需求 | 联动、计算规则、触发器（需分析泛微能力是否支持） |
| "实时"、"即时" | 即时性需求 | 联动、刷新、查询时计算 |
| "核对"、"对比" | 数据比对需求 | 联动展示、只读显示（泛微自动对比能力有限，需说明手动操作） |

**禁止行为**：不提取验收标准直接开始设计。

### 第二步：能力推导

> 依据：`references/derivation-rules.md` + `references/capability-map.md` + `references/modeling-sdk-reference.md`

对每个能力域的子需求，从终点能力逆向推导完整依赖链。推导过程中自然完成数据结构分析。

**输入**：场景定位结果 + 需求文档
**输出**：
- 依赖链（倒推结果）
- 执行顺序（正排结果）
- 数据结构（字段清单、浏览框规划、依赖关系）
- 建模要素对照表（表单/模块/查询/浏览框）

**推导过程**：

1. **确定终点能力** — 从需求描述找出"最终要做出什么"（如菜单、查询列表）
2. **逆向推导依赖链** — 从终点一路倒推到应用/表单起点
3. **了解平台能力** — 推导数据结构前，按需读取 `references/modeling-sdk-reference.md` 中涉及到的**对应章节**（文档按组件分 10 个章节，只读本次设计涉及的组件章节），明确平台对每类组件提供了什么能力和约束，建立结构选项清单。
4. **实体结构分析（阻断检查，必须输出结论表后才能继续）** — 对需求中的每个业务实体，必须逐一回答以下问题并输出结论表：
   - 该实体是否有子实体？
   - 增删查时，想不想在同一页面看到主信息和子实体明细？
   - 结论：独立表单 or 主从表单？理由是什么？

   **输出格式**（禁止跳过此表）：
   ```
   | 业务实体 | 有无子实体 | 想同页看到？ | 结论（独立/主从） | 理由 |
   |---------|-----------|-------------|----------------|------|
   | 房间 | 有（家具清单） | 是 | 主从表单 | 管理员配家具时想在房间页面直接看到 |
   | 公寓 | 无 | - | 独立表单 | 无子实体 |
   ```

   **禁止行为**：不分析直接一个实体一张表。
   判断依据详见 `modeling-rules.md` "执行前阻断检查" 和 `modeling-sdk-reference.md` "明细表判断" 章节。

5. **推导数据结构** — 实体结构分析完成后，按结论列字段：
   - **列出字段** — 根据结构决定列出字段：主从表单分主表字段 + 明细表字段，独立表单各自列出
   - **判断字段类型** — 每个字段的逻辑类型
   - **分析浏览框依赖** — 是否有环形依赖？
6. **正向排序** — 倒推结果反过来就是执行顺序

**建模要素对照表**（必须输出）：

```
| 表单 | 模块 | 查询 | 浏览框 |
|------|------|------|--------|
| 通知公告 | 通知公告 | 通知公告管理（科技部） | 无 |
| | | 通知公告列表（申报人） | |
```

校验：表单、模块、查询列数量必须相等；任何一行中模块或查询为空必须说明原因。

**跳过字段清单**（如有自定义浏览框依赖）：

```
| 表单 | 跳过字段 | 依赖的浏览框 | 补加时机 |
|------|---------|------------|---------|
| 初审审核 | project_ref | 项目浏览框 | 浏览框创建后 |
```

### 第三步：依赖分析 + 执行步骤设计

> 依据：`references/derivation-rules.md` 第五、六节 + `references/capability-map.md`

基于第二步的推导结果，确定执行步骤的拓扑顺序，编写每步的具体操作。

**输入**：第二步产出的依赖链和数据结构
**输出**：执行步骤列表（每步包含：步骤名称、执行方式、具体操作、预期结果、验证方式）

**执行顺序参考**：

| 步骤 | 动作 | 产出 | 下游谁需要 |
|------|------|------|-----------|
| 1 | 确认/创建应用 | 应用 ID | 模块 |
| 2 | 创建表单 + 字段 | 表单 ID + 字段列表 | 模块、查询、浏览框、布局 |
| 3 | 刷新缓存 | — | 让 label 生效 |
| 4 | 创建自定义浏览框 | 浏览框配置 | 表单字段 |
| 5 | 补加跳过字段 | 字段列表 | — |
| 6 | 创建模块 | 模块 ID | 查询、布局、联动 |
| 7 | 创建查询列表 + 显示字段 | 查询配置 | 菜单、快捷搜索 |
| 8 | 配置布局 | 布局 JSON | — |
| 9 | 配置快捷搜索 | 快捷搜索条件 | — |
| 10 | 创建菜单 | 菜单项 | — |

**按需裁剪**：不是每一步都要做，根据需求提取对应的步骤子集。

**自定义浏览框字段处理**：
- 创建表单时跳过依赖"尚未创建的自定义浏览框"的字段
- 创建浏览框后，用 `add_fields_to_form` 补加
- 补加后验证字段类型（自定义浏览框 type=161，系统浏览框 type=8）

### 第四步：填充 SDK

> 依据：`references/modeling-sdk-reference.md`（参数格式）

第二步已读过 SDK 文档的思考点，这里专注把分析结果填入参数格式。

**输入**：第三步的执行步骤 + 第二步的数据结构
**输出**：每个步骤的 SDK 调用参数（写入开发设计文档）

**流程**：

1. **确定 SDK tool** — 从 capability-map.md 查找对应能力
2. **读取参数格式** — 查看 tool 的参数定义（类型、必填、取值范围）
3. **填充参数** — 把第二步的分析结果填入参数格式
5. **调用查询方法辅助决策**（如需要）：
   - `form_list_browsers` — 判断系统浏览框是否存在
   - `browser_list_browsers` — 判断自定义浏览框是否已存在
   - `form_list_form_fields` — 获取表单字段用于构建浏览框配置
   - `modeling_list_apps` — 判断应用是否已存在

**示例**：创建浏览框

```
步骤：创建项目浏览框
SDK tool：browser_create_browser
参数格式：browser_name(string), form_id(int), app_id(int), fields(array<object>), default_filter(string)

思考点分析：
- 展示字段：项目名称、项目编号、项目类型（核心辨识，3 个够了）
- 链接字段（istitle）：项目名称（文本类型，唯一，最代表性）
- 查询字段（isquery）：项目名称、项目状态（能缩小范围）
- 默认过滤：project_status='已发布'（只显示已发布的项目）

参数填充：
{
  "browser_name": "项目浏览框",
  "form_id": 123,
  "app_id": 45,
  "default_filter": "project_status='已发布'",
  "fields": [
    {"fieldname": "project_name", "istitle": 1, "displayorder": 0},
    {"fieldname": "project_code", "isquery": 1, "displayorder": 1},
    {"fieldname": "project_type", "displayorder": 2},
    {"fieldname": "project_status", "isquery": 1, "displayorder": 3}
  ]
}
```

### 第六步：生成三份文档

一次性生成三个文件，结构分别见对应模板：

- `project/{项目名}/01-数据结构设计.md` — 结构见 `template-data-structure.md`
- `project/{项目名}/02-开发设计.md` — 结构见 `template-dev-design.md`
- `project/{项目名}/03-测试文档.md` — 结构见 `template-test.md`

**数据结构设计文档**包含：
- 表结构（字段清单，按依赖顺序排列）
- 浏览框规划（自定义浏览框 + 系统浏览框引用）
- 依赖分析（依赖关系图、环形依赖处理、字段补加计划）
- 建模要素对照表

**开发设计文档**包含：
- 需求映射（需求编号 → 泛微能力 → 执行方式）
- 数据模型（完整复制数据结构设计）
- 执行步骤（每步包含 SDK tool + 完整参数 + 预期结果 + 验证方式）
- 前端效果展示（菜单、布局、查询页面）
- 不支持的功能

**测试文档**包含：
- 正常流程测试
- 异常流程测试
- 边界用例测试
- 权限测试

生成后告诉用户：
> "方案已出，在 `project/{项目名}/` 下：
> - `01-数据结构设计.md` — 表结构 + 字段 + 浏览框 + 依赖分析
> - `02-开发设计.md` — 执行步骤 + 前端效果
> - `03-测试文档.md` — 测试用例
>
> 确认后进入执行阶段。"

**不要在三份文档生成过程中穿插确认环节。** 一次出齐，等用户统一审阅。

### 第七步：验收标准核对（阻断检查）

> 设计完成后必须完成，禁止跳过。

逐条核对需求文档中的验收标准，确保每条都有对应设计。

**输入**：第一步半提取的验收标准 + 三份设计文档
**输出**：验收标准覆盖表（写入开发设计文档）

**核对流程**：

1. **逐条对照**：对第一步半提取的每条验收标准，在设计文档中找到对应设计点
2. **标记状态**：
   - ✓ 已覆盖：设计文档中有明确对应
   - ✗ 遗漏：设计文档中没有对应，需要补充设计
   - ⊘ 不支持：泛微能力不支持，在"不支持的功能"中说明原因和替代方案
3. **补充遗漏**：发现遗漏项时，必须补充设计后再交付，不能留给执行阶段

**输出格式**（必须输出，写入开发设计文档）：

```
【验收标准覆盖表】
| 需求编号 | 验收标准 | 对应设计点 | 状态 |
|---------|---------|-----------|------|
| F1-1 | 可以创建公寓、楼栋、房间三级结构 | 3张表单 + 层级浏览框 | ✓ 已覆盖 |
| F2-2 | 只能选空置房 | 需创建"空置房间浏览框" | ✗ 遗漏，已补充设计 |
| F2-3 | 入住后房间状态自动变"已入住" | 需配置联动或说明手动操作 | ⊘ 不支持，手动操作 |
```

**禁止行为**：
- 不核对验收标准就交付文档
- 发现遗漏但不补充设计
- 把"不支持"当作万能的遗漏借口（必须先分析是否有替代方案）

## 反面模式

| 反面模式 | 为什么不对 | 正确做法 |
|---------|-----------|---------|
| 功能设计没有对应的需求编号 | 自作主张，和需求对不上 | 每个设计项都标注需求编号 |
| 执行方式写"待定" | 下一步没法干 | 能自动标自动，不能自动给手动步骤 |
| 测试用例只写正常流程 | 边界情况一测就挂 | 正常 + 异常 + 边界都覆盖 |
| 脱离泛微能力设计 | 做出来发现跑不动 | 做不了直接说，别糊弄 |
| 执行步骤顺序错误 | 创建表单时引用的浏览框还不存在 | 先做依赖分析，按拓扑排序排步骤 |
| 环形依赖未处理 | 表单引用自身导致死循环 | 跳过自关联字段，等浏览框创建后补加 |
| 跳过字段未记录 | 执行时遗漏补加步骤，字段丢失 | 输出"跳过字段清单" |
| 三份文档分批生成、中间卡确认 | 需求文档已确认时纯属拖节奏 | 一次出齐，统一审阅 |
| 开发设计文档 fields 只写字段名不写类型 | SDK 自动推断会覆盖设计值 | fields 必须携带完整类型定义 |
| 不看 references/modeling-sdk-reference.md 就填参数 | 参数格式错、类型错 | 每个 tool 的参数格式和思考点都在 SDK 文档里 |
| 设计文档写物理类型（varchar/int/text） | 和执行阶段 SDK 的逻辑类型对不上，文档和数据库不一致 | 统一用逻辑类型（dropdown/textarea/date/browser 等），见字段类型规则 |
| 设计组件前不读 SDK 参考文档 | 不了解平台能力和约束，凭直觉设计方案，该用明细表的写成平铺字段、该用联动的写成手动填写 | 设计任何组件前，先读 `modeling-sdk-reference.md` 中对应工具的思考点 |
| 执行步骤写"各查询的快捷搜索条件" | 模糊描述，执行者还得自己再想一遍 | 每个查询配哪些字段必须逐一列明 |
| 设计完成后不自检 | 把"思考的活儿"推给执行阶段 | 每个步骤必须能直接执行，不留临场发挥空间 |
| 步骤数量不核对 | 漏设计导致执行时缺步骤 | 功能清单推导出的操作数 = 文档步骤数 |
| 跳过验收标准提取 | 设计时遗漏需求细节（"自动"、"只能"等约束条件） | 第一步半必须提取验收标准并标注关键词 |
| 跳过验收标准核对 | 交付的设计文档有遗漏，执行阶段才发现 | 第七步必须逐条核对，输出覆盖表 |
| 把"不支持"当万能借口 | 用"泛微不支持"掩盖设计不充分 | 必须先分析替代方案，确实不支持才能标记 |
| "自动"需求不分析实现方式 | 执行时发现"自动"做不了，临时改方案 | 对每个"自动"分析：联动？计算规则？手动？ |
