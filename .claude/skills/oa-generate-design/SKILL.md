# 方案设计 — 泛微二开

> 拿着需求文档，逐条功能清单分析，对照泛微能力，一次性出齐三份文档（数据结构+开发设计+测试）。不卡确认、不凑字数、不做空中楼阁。

---

## 核心原则

**有依据才设计。** 每个设计项都对应需求文档编号，不自编需求。没找到 `01-需求文档.md` 就告诉用户先完成需求分析。

**能力文档是边界。** 以 `references/capability-map.md`（能做什么）和 `references/modeling-sdk-reference.md`（怎么调用）为准。做不了直说，别糊弄。

**一次出齐，不卡确认。** 需求文档已确认的前提下，三份文档一次性生成，不等用户确认中间产物。

**字段类型必须传递。** 开发设计文档执行步骤中的 fields 参数必须携带完整字段类型定义（name、label、type、db_type/length/browser_id/options），与数据结构设计文档逐字一致。

---

## 设计依据

方案设计依赖三类文档：

| 类别 | 文档 | 作用 |
|------|------|------|
| **需求文档** | `project/{项目名}/01-需求文档.md` | 功能清单、角色权限、业务流程、验收标准 |
| **能力文档** | `references/capability-map.md`（能力地图）+ `references/modeling-sdk-reference.md`（SDK 参数） | 泛微能做什么、每个 tool 的参数格式和思考点 |
| **设计规范文档** | `.claude/rules/modeling-rules.md` + `references/derivation-rules.md` + `references/scenario-classification.md` | 怎么思考、怎么推导、怎么决策 |

---

## 何时激活

**一定要用：**
- 需求文档存在，用户说"出方案"、"写开发设计"、"做技术方案"、"第二步"、"怎么落地"
- 用户拿着需求文档问实现方案

**可以跳过：**
- 需求还没理清（回去走第一步）
- 就调一个已知接口、改一个已知字段

## 执行流程

### 第一步：场景定位

> 依据：`references/scenario-classification.md`

读取需求文档，逐条功能清单扫描关键词，判断属于哪个能力域。

**输入**：需求文档功能清单
**输出**：每条功能的能力域判定

```
【场景定位】
- F1 通知公告：命中"发布/编辑/停用/查看" → 建模引擎
- F2 项目审批：命中"审批/节点/流转" → 流程引擎
- F3 每日统计：命中"每日/自动执行" → 定时任务
```

多域混合时，按域拆分为独立子需求，分别走后续流程。

---

### 第二步：能力推导

> 依据：`references/derivation-rules.md` + `references/capability-map.md`

对每个能力域的子需求，从终点能力逆向推导完整依赖链。推导过程中自然完成数据结构分析。

**输入**：场景定位结果 + 需求文档
**输出**：
- 依赖链（倒推结果）
- 执行顺序（正排结果）
- 数据结构（字段清单、浏览框规划、依赖关系）
- 建模要素对照表（表单/模块/查询/浏览框）

**推导过程**：

1. **确定终点能力** — 从需求描述找出"最终要做出什么"（如菜单、查询列表）
2. **逆向推导依赖链** — 从终点一路倒推到应用/表单起点
3. **推导数据结构** — 推导到"需要创建表单"时，自然进入字段分析：
   - 需要哪些字段？
   - 字段是什么类型（文本、浏览框、选择框）？
   - 哪些字段依赖浏览框？浏览框依赖哪些表单？
   - 是否有环形依赖？
4. **正向排序** — 倒推结果反过来就是执行顺序

**建模要素对照表**（必须输出）：

```
| 表单 | 模块 | 查询 | 浏览框 |
|------|------|------|--------|
| 通知公告 | 通知公告 | 通知公告管理（科技部） | 无 |
| | | 通知公告列表（申报人） | |
```

校验：表单、模块、查询列数量必须相等；任何一行中模块或查询为空必须说明原因。

**跳过字段清单**（如有自定义浏览框依赖）：

```
| 表单 | 跳过字段 | 依赖的浏览框 | 补加时机 |
|------|---------|------------|---------|
| 初审审核 | project_ref | 项目浏览框 | 浏览框创建后 |
```

---

### 第三步：依赖分析 + 执行步骤设计

> 依据：`references/derivation-rules.md` 第五、六节 + `references/capability-map.md`

基于第二步的推导结果，确定执行步骤的拓扑顺序，编写每步的具体操作。

**输入**：第二步产出的依赖链和数据结构
**输出**：执行步骤列表（每步包含：步骤名称、执行方式、具体操作、预期结果、验证方式）

**执行顺序参考**：

| 步骤 | 动作 | 产出 | 下游谁需要 |
|------|------|------|-----------|
| 1 | 确认/创建应用 | 应用 ID | 模块 |
| 2 | 创建表单 + 字段 | 表单 ID + 字段列表 | 模块、查询、浏览框、布局 |
| 3 | 刷新缓存 | — | 让 label 生效 |
| 4 | 创建自定义浏览框 | 浏览框配置 | 表单字段 |
| 5 | 补加跳过字段 | 字段列表 | — |
| 6 | 创建模块 | 模块 ID | 查询、布局、联动 |
| 7 | 创建查询列表 + 显示字段 | 查询配置 | 菜单、快捷搜索 |
| 8 | 配置布局 | 布局 JSON | — |
| 9 | 配置快捷搜索 | 快捷搜索条件 | — |
| 10 | 创建菜单 | 菜单项 | — |

**按需裁剪**：不是每一步都要做，根据需求提取对应的步骤子集。

**自定义浏览框字段处理**：
- 创建表单时跳过依赖"尚未创建的自定义浏览框"的字段
- 创建浏览框后，用 `add_fields_to_form` 补加
- 补加后验证字段类型（自定义浏览框 type=161，系统浏览框 type=8）

---

### 第四步：填充 SDK

> 依据：`references/modeling-sdk-reference.md`（每个 tool 的参数格式和思考点）

对每个执行步骤，确定对应的 SDK tool，结合需求分析结果和 SDK 思考点，得到完整的 SDK 参数。

**输入**：第三步的执行步骤 + 第二步的数据结构 + capability-map.md 中的思考点
**输出**：每个步骤的 SDK 调用参数（写入开发设计文档）

**流程**：

1. **确定 SDK tool** — 从 capability-map.md 查找对应能力
2. **读取参数格式** — 查看 tool 的参数定义（类型、必填、取值范围）
3. **读取思考点** — 查看 tool 的思考点（调用时需要业务分析的内容）
4. **填充参数** — 结合需求分析结果和思考点，填写参数值
5. **调用查询方法辅助决策**（如需要）：
   - `form_list_browsers` — 判断系统浏览框是否存在
   - `browser_list_browsers` — 判断自定义浏览框是否已存在
   - `form_list_form_fields` — 获取表单字段用于构建浏览框配置
   - `modeling_list_apps` — 判断应用是否已存在

**示例**：创建浏览框

```
步骤：创建项目浏览框
SDK tool：browser_create_browser
参数格式：browser_name(string), form_id(int), app_id(int), fields(array<object>), default_filter(string)

思考点分析：
- 展示字段：项目名称、项目编号、项目类型（核心辨识，3 个够了）
- 链接字段（istitle）：项目名称（文本类型，唯一，最代表性）
- 查询字段（isquery）：项目名称、项目状态（能缩小范围）
- 默认过滤：project_status='已发布'（只显示已发布的项目）

参数填充：
{
  "browser_name": "项目浏览框",
  "form_id": 123,
  "app_id": 45,
  "default_filter": "project_status='已发布'",
  "fields": [
    {"fieldname": "project_name", "istitle": 1, "displayorder": 0},
    {"fieldname": "project_code", "isquery": 1, "displayorder": 1},
    {"fieldname": "project_type", "displayorder": 2},
    {"fieldname": "project_status", "isquery": 1, "displayorder": 3}
  ]
}
```

### 第五步：标注"不支持项"

> 依据：`references/capability-map.md` 不支持的能力 + `references/scenario-classification.md` 不支持的能力

对照需求功能清单，逐一检查泛微原生是否支持。不支持的功能明确标注，给出替代方案建议。

**输入**：需求功能清单 + 能力文档中的"不支持能力"
**输出**：不支持项清单（写入开发设计文档）

```
| 需求编号 | 功能 | 原因 | 替代方案 |
|---------|------|------|---------|
| F3 | 过期自动标记 | 泛微不支持定时任务自动更新状态 | 定时脚本或在查询时动态判断 |
```

---

### 第六步：生成三份文档

一次性生成三个文件，结构分别见对应模板：

- `project/{项目名}/01-数据结构设计.md` — 结构见 `template-data-structure.md`
- `project/{项目名}/02-开发设计.md` — 结构见 `template-dev-design.md`
- `project/{项目名}/03-测试文档.md` — 结构见 `template-test.md`

**数据结构设计文档**包含：
- 表结构（字段清单，按依赖顺序排列）
- 浏览框规划（自定义浏览框 + 系统浏览框引用）
- 依赖分析（依赖关系图、环形依赖处理、字段补加计划）
- 建模要素对照表

**开发设计文档**包含：
- 需求映射（需求编号 → 泛微能力 → 执行方式）
- 数据模型（完整复制数据结构设计）
- 执行步骤（每步包含 SDK tool + 完整参数 + 预期结果 + 验证方式）
- 前端效果展示（菜单、布局、查询页面）
- 不支持的功能

**测试文档**包含：
- 正常流程测试
- 异常流程测试
- 边界用例测试
- 权限测试

生成后告诉用户：
> "方案已出，在 `project/{项目名}/` 下：
> - `01-数据结构设计.md` — 表结构 + 字段 + 浏览框 + 依赖分析
> - `02-开发设计.md` — 执行步骤 + 前端效果
> - `03-测试文档.md` — 测试用例
>
> 确认后进入执行阶段。"

**不要在三份文档生成过程中穿插确认环节。** 一次出齐，等用户统一审阅。

## 反面模式

| 反面模式 | 为什么不对 | 正确做法 |
|---------|-----------|---------|
| 功能设计没有对应的需求编号 | 自作主张，和需求对不上 | 每个设计项都标注需求编号 |
| 执行方式写"待定" | 下一步没法干 | 能自动标自动，不能自动给手动步骤 |
| 测试用例只写正常流程 | 边界情况一测就挂 | 正常 + 异常 + 边界都覆盖 |
| 脱离泛微能力设计 | 做出来发现跑不动 | 做不了直接说，别糊弄 |
| 执行步骤顺序错误 | 创建表单时引用的浏览框还不存在 | 先做依赖分析，按拓扑排序排步骤 |
| 环形依赖未处理 | 表单引用自身导致死循环 | 跳过自关联字段，等浏览框创建后补加 |
| 跳过字段未记录 | 执行时遗漏补加步骤，字段丢失 | 输出"跳过字段清单" |
| 三份文档分批生成、中间卡确认 | 需求文档已确认时纯属拖节奏 | 一次出齐，统一审阅 |
| 开发设计文档 fields 只写字段名不写类型 | SDK 自动推断会覆盖设计值 | fields 必须携带完整类型定义 |
| 不看 modeling-sdk-reference.md 就填参数 | 参数格式错、类型错 | 每个 tool 的参数格式和思考点都在 SDK 文档里 |

## 与上下游的衔接

> 本技能是**泛微二开标准流程的第二步**，完整流程见 `docs/oa-development-process.md`。

**上游输入：** `project/{项目名}/01-需求文档.md`（第一步产出）

**下游输出：**
- `project/{项目名}/01-数据结构设计.md` — 表结构 + 字段 + 浏览框 + 依赖关系
- `project/{项目名}/02-开发设计.md` — 进入第三步执行（`oa-execute-dev`）
- `project/{项目名}/03-测试文档.md` — 进入第四步测试（`oa-test-verify`）
