# 测试验收 — 泛微二开

> 按测试文档逐条跑用例，验证开发结果。发现问题分类处理：工具问题记录不动手，数据问题自动修正重跑。

---

## 核心原则

**严格按测试文档来。** 不自己编用例、不跳过、不挑容易的先跑。正常流程、异常流程、边界用例都要覆盖。

**测试数据隔离。** 测试产生的数据加 `_test` 标记，测完清理，不污染正式数据。详细规则见 `references/dirty-data-cleanup.md`。

**工具问题不能动。** SKILL、SDK、MCP tool 等工具有疑似 bug → 记录标注"疑似工具异常"，等人工确认。**绝对不改工具代码。** 工具是基础设施，改坏了影响面大。

**非工具问题自动修。** 数据不对、配置错了、参数传错、业务逻辑偏差 → 直接修正 → 重跑验证。不需要等人工确认。

**表层底层都要验。** 用户看的是页面不是数据库。SQL 查表有数据不等于用户能用。测试方式要和用户实际使用方式一致。

**报告要能看。** 通过率、哪些没过、为什么没过、修了重跑的结果——让用户一眼看出"能不能上线"。

---

## 何时激活

**一定要用：**
- 执行完成，用户说"测试"、"验收"、"第五步"、"跑测试用例"
- 用户说"验证一下"、"看看对不对"、"跑一遍"
- `{项目名}/03-测试文档.md` 存在且 `{项目名}/04-执行记录.md` 显示执行完成

**可以跳过：**
- 执行还没完成（回去走第四步）
- 就单独验证某一条 SQL 或某一个功能点

## 执行流程

### 前置检查

开始前确认：
- [ ] `{项目名}/03-测试文档.md` 存在
- [ ] `{项目名}/04-执行记录.md` 存在且执行完成
- [ ] 测试环境可用（MCP Server、数据库、前端页面可访问）

全部确认后直接开始。

### 创建测试报告

在 `{项目名}/` 下创建 `05-测试报告.md`。报告结构详见 `template-test-report.md`。

### 逐条跑用例

按测试文档序号逐一执行。

**执行前：** "现在跑第 T 条用例 — {测试场景}"

**执行中：** 按文档步骤操作，验证预期结果。

**执行后：** 记录结果到报告文件，格式：

```markdown
### T{序号}：{测试场景}
- 对应需求：F{编号}
- 测试方式：{手动验证 / SDK 调用 / SQL 查询}
- 预期结果：{文档写的}
- 实际结果：{实际看到的}
- 状态：✅ 通过 / ❌ 失败 / ⚠️ 疑似工具异常
- 完成时间：{HH:mm}
```

### 失败处理

用例失败时，先判断原因类型：

**工具异常**（SDK/MCP 返回报错、工具行为与设计文档不一致）→ 记录标 ⚠️，不动手。

**非工具异常**（数据/配置/参数/逻辑错误）→ 分析 → 修正 → 重跑 → 验证。

**判断不确定时：** 告诉用户"这条用例没过，看起来像 XX 问题，你帮确认下是工具问题还是配置问题？"

### 重跑规则

修正后的用例：通过 → 标记"重跑通过"；仍失败 → 标记"重跑仍失败"，记录详情。

### 生成汇总报告

所有用例跑完后，在报告文件末尾添加汇总段落。格式见 `template-test-report.md`。

告诉用户：
> "测试完成，通过率 X%。{通过/未通过}的详情在 `05-测试报告.md` 里。{如有：有 N 条疑似工具异常，需你确认后再处理。}"

## 反面模式

| 反面模式 | 为什么不对 | 正确做法 |
|---------|-----------|---------|
| 只跑正常流程，跳过异常边界 | 异常一触发就崩 | 所有用例都要跑 |
| 测试失败改工具代码 | 基础设施改坏影响面大 | 记录待人工确认 |
| SQL 查表有数据就算过 | 用户看的是页面不是库 | 表层底层都要验 |
| 测试数据混进正式数据 | 影响正式使用 | 隔离标记，测完清理 |
| 报告只写"通过 X 条" | 看不出能不能上线 | 通过率、详情、结论都写 |
| 自己编测试用例 | 和需求对不上 | 严格按文档来 |

## 正面模式

- 所有用例都跑，不跳过不编造
- 工具问题不动手，记录待确认
- 数据问题自动修，修完重跑
- 表层（页面）底层（SQL）都要验
- 测试数据隔离，测完清理
- 报告清晰，结论明确
